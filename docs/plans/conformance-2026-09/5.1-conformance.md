# Leaf 5.1 — ceph/s3-tests conformance baseline

## Goal
Run the industry-standard ceph/s3-tests suite (unmodified) against zeta-object,
produce a pass/fail matrix, and triage every failure into exactly one of:
[a] REAL BUG in a feature zeta-object claims (README feature list) → fix it;
[b] DOCUMENTED DIVERGENCE (behavior differs from AWS deliberately — the
CLAUDE.md divergences list) → record in the matrix with the divergence ref;
[c] OUT-OF-SCOPE FEATURE (versioning, lock, SSE, lifecycle, tagging, policy,
ACL enforcement, storage class, CORS, website, s3select, logging, IAM/STS) →
deselected via pytest markers, never fixed.

## Setup (all inside the repo, gitignored where noted)

1. `vendor/s3-tests/` (gitignored — add to .gitignore): shallow-clone
   github.com/ceph/s3-tests. Python venv via `python3 -m venv` +
   `pip install -r requirements.txt` per its README (boto3, pytest; tox NOT
   required — invoke pytest directly to avoid tox env management).
2. `scripts/conformance/s3tests.conf` (COMMITTED — it is the config that
   makes the suite reproducible; contains only localhost + zetaadmin
   placeholder creds, which are the documented defaults): port from
   ZETAOBJECT_CONFORMANCE_PORT (default 18499), is_secure=false.

   DECISION — run against PLAIN HTTP: zeta-object is HTTPS-only. Add a
   conformance-only plain-HTTP listener? NO — instead generate a temp cert
   and set `ssl_verify=false` in the s3tests config (the suite supports
   self-signed certs via ssl_verify). If boto3 rejects the cert despite
   ssl_verify=false, fall back: add `ZETAOBJECT_CONFORMANCE_HTTP=1` env that
   starts a second plain-HTTP listener on the conformance port (one
   http.Server, no TLS — conformance-only, documented in main.go). Prefer
   the ssl_verify path; only implement the env fallback if needed.
3. Server lifecycle: mirror scripts/e2e/run-e2e.sh — build, free port, temp
   dataDir, trap kill. Script: `scripts/conformance/run-conformance.sh`
   (COMMITTED).
4. Test selection: `pytest s3tests/functional -m` with a deselect marker
   expression covering the out-of-scope list above (put the exact `-m`
   expression in run-conformance.sh; start permissive, tighten after the
   first full run shows the collection size). Suite supports
   `-k`-narrowing too. Target: collect 300-600 tests, run < 15 min.

## The run + deliverables

5. First full run → capture the results (pytest -v output →
   `docs/conformance/2026-09-28-matrix.md`, COMMITTED):
   table of test group → pass/fail counts → per-failure triage tag
   [a]/[b]/[c] with one-line reason. Group by s3tests test file/section
   (bucket lifecycle, object CRUD, listing, multipart, copy, conditional,
   range, presigned, auth).
6. Triage pass: for every [a], write a RED reproduction (unit or e2e), fix,
   GREEN, re-run the suite, update the matrix. Expected [a] count: 0-6
   (zeta-object's features are heavily tested already; the long tail is
   [b]/[c]). If [a] > 10, STOP and report the list before fixing —
   orchestrator prioritizes.
7. Make target: `make conformance` → runs run-conformance.sh; prints the
   matrix summary (pass/fail per group) and exits non-zero ONLY if a
   previously-passing test regressed (store last-known-good counts in
   scripts/conformance/baseline.txt, COMMITTED). New failures vs baseline =
   gate failure. This makes the suite a regression ratchet without demanding
   100% conformance.
8. README: one paragraph under a "Protocol conformance" heading pointing at
   the matrix + how to run (leaf 2.7's doc is yours to extend — one section
   only).

## STOP clauses
- Suite will not run against HTTPS/self-signed after 2 attempts → implement
  the ZETAOBJECT_CONFORMANCE_HTTP fallback (documented above) and continue.
- [a] failures > 10 → report before fixing.
- boto2 variants: skip entirely (boto2 install is fragile; boto3 dir is the
  maintained surface).

## Gates
go build/vet/test green (any [a] fixes come with RED/GREEN);
make conformance completes; matrix + baseline committed (orchestrator
commits). Coverage floor holds.
Do NOT commit.
