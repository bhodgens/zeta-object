# Leaf 5.2 — Client interop matrix (boto3 + mc)

## Goal
Prove the same operations produce identical observable outcomes through
three independent S3 clients: aws-cli v2 (existing e2e), python boto3,
MinIO client `mc`. The botocore `<Error>` xmlns bug (found and fixed by the
e2e suite) is the class this guards: client-specific parsing breaking on
wire-format quirks.

## Setup

1. `scripts/e2e/interop-lib.sh` (NEW, COMMITTED): the shared scenario
   table — a bash function per scenario performing client-neutral
   assertions (curl already proves wire-level truth; the matrix asserts
   CLIENT-level parity: same status codes, same error codes parsed by that
   client's own parser, same observable data). Scenarios (one per e2e case
   group): bucket create/head/list/delete, object put/get round-trip,
   unicode key, error codes (NoSuchBucket/NoSuchKey/AccessDenied),
   listing with prefix, range GET, multipart round-trip, presigned GET
   (boto3: generate_presigned_url; mc: `mc share download`), copy,
   batch delete.
2. boto3: the ceph-suite venv from leaf 5.1 already provides it — reuse
   `vendor/s3-tests/.venv` if present, else create `vendor/boto3-venv`
   (gitignored) with boto3 only. A small python helper
   `scripts/e2e/boto3-runner.py` (COMMITTED) reads scenario + args from
   argv/stdin, executes via boto3 client pointed at the endpoint
   (verify=False), prints machine-readable status + parsed error code +
   payload hash, exits 0/1.
3. `mc`: `vendor/mc` binary (gitignored; downloaded by run-conformance-style
   bootstrap in the case file if absent — `curl` the official release for
   the host arch into a temp dir, no system install). Configure via
   `mc alias set zetaobject https://localhost:PORT minioadmin minioadmin
   --insecure`.

## Cases (NEW e2e case files)

- `cases/12-interop-boto3.sh`: iterate the scenario table, run each through
  boto3-runner.py; assert parity with the aws-cli e2e outcomes (expected
  statuses/codes are hardcoded from the existing cases — the suite IS the
  expected-behavior spec).
- `cases/13-interop-mc.sh`: same via mc. mc quirks to tolerate: `mc` prints
  JSON with `--json`; status extraction from its exit code + error JSON
  `Code` field. If a scenario is impossible in mc (e.g. raw conditional
  headers), assert the closest observable (its error message contains the
  code) and comment why.

## Parity rule (frozen)

A scenario passes when: client exits success AND observed data matches, OR
client fails with the SAME S3 error code the aws-cli e2e case asserts.
Client-specific failures to PARSE the response are findings (that is the
whole point) → triage like 5.1: [a] fix wire format, [b] divergence, [c]
client bug → document + skip with reason comment.
