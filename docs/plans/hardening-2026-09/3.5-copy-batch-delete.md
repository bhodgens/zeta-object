# Leaf 3.5 — CopyObject + DeleteObjects (batch)

## Goal
Implement x-amz-copy-source CopyObject and POST /bucket?delete batch delete.
You own object_handlers.go, bucket_handlers.go (routing in main.go rootHandler,
minimal), types.go (append-only structs), copy_batch_test.go (NEW).

## CopyObject (PUT object with x-amz-copy-source header)

1. Detect in putObjectHandler (or before it in rootHandler — your choice,
   prefer handler): header x-amz-copy-source present → copyObjectHandler.
2. Parse source: `bucket/key` or `/bucket/key` (URL-decode; optional
   `?versionId=` suffix — reject with NotImplemented/501 if versionId present).
3. Source must exist (NoSuchKey/404), source bucket must exist
   (NoSuchBucket/404). Same-bucket and cross-bucket copies both supported.
4. Copy = read source data + source meta, write new object at destination key
   using the storage.go atomic helpers + lockObject (server-side copy, NOT a
   client re-upload). New ETag = MD5 of data (plain copy, S3 computes fresh).
   Metadata: copy source Content-Type + x-amz-meta-* unless
   x-amz-metadata-directive=REPLACE with new headers from the request
   (support REPLACE and COPY, default COPY; other values → InvalidArgument).
5. Response: 200 with XML CopyObjectResult{ETag quoted, LastModified}. Note
   S3 quirk: 200 with XML body, Content-Type application/xml.
6. Destination = the PUT's own bucket/key. x-amz-copy-source == destination →
   InvalidRequest/400 (S3 rejects same-source-same-dest without directive).
7. after_upload actions fire for the new object (reuse triggerActions site).

## DeleteObjects (POST /bucket?delete)

1. Route in rootHandler: bucket-level POST with `delete` query param →
   deleteObjectsHandler. (Bucket-level POST currently 405s — add route.)
2. Body XML: <Delete><Object><Key>k</Key></Object>...<Quiet>true|false</Quiet></Delete>.
   Parse; MalformedXML/400 on bad XML; empty Object list → MalformedXML.
   Cap at 1000 keys → MalformedXML (S3 rule).
3. For each key: reuse the same deletion logic as single deleteObjectHandler —
   extract its core into `func deleteObjectCore(bucketPath, bucketName, key
   string) error` (your refactor of object_handlers.go) returning error only.
4. Response XML DeleteResult: per-key <Deleted><Key>k</Key></Deleted> (or
   only errors when Quiet=true). Individual key errors (none currently
   possible — deletion of missing key succeeds per S3) → <Error> entries if
   internal error occurs; include Key + Code.
5. after_delete actions fire per deleted key (existing core does it or you
   add it — single place).

## Tests
Copy: happy path same bucket, cross bucket, meta COPY preserved, REPLACE
changes content type, missing source 404, same-src-dst 400, response XML
shape. DeleteObjects: two keys deleted + result XML, Quiet mode shape,
missing keys report Deleted (S3 semantics), malformed XML 400, >1000 keys 400.
