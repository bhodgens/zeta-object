# Leaf 4.8 — Concurrency stress suite

## Goal
The e2e has one 20-iteration bash PUT/GET loop. A Go-native stress suite under
-race proves the locking contracts at higher concurrency and on shared state
the e2e cannot reach.

## Files you own
concurrency_stress_test.go (NEW). NO production edits — a -race failure here
is a REAL finding: STOP and report it with the failing interleaving.

## Tests (all run under the race detector; keep each under ~2s)

1. ConcurrentSameKeyPutGetDelete: 8 goroutines × 50 iterations mixing
   PUT/GET/DELETE on ONE key through the handlers (httptest, auth bypass like
   sibling tests). Invariants: GET returns either 200 with bytes from SOME
   complete PUT or 404; NEVER a torn body (assert body is one of the written
   values, byte-exact), never 500.
2. ConcurrentDifferentKeys: 8 goroutines × 50 on distinct keys → all succeed,
   final list shows all keys (no lost writes).
3. ConcurrentUploadPartAbort: one session; 5 goroutines upload distinct parts
   while a 6th aborts; final state is CONSISTENT: either all parts recorded
   (abort lost the race for every part) or session gone — never partial meta
   with missing _parts dir nor a panic. (getMultipartLock should guarantee
   this.)
4. ConcurrentCreateDeleteBucket: alternate create/delete of the same bucket
   name 30×, plus a reader goroutine listing buckets throughout → no panic,
   ListBuckets output always parseable XML.
5. ConcurrentCompleteMultipart: complete racing a final uploadPart on the
   same session → either NoSuchUpload or success, never a torn final object
   (assert final object size equals sum of the parts actually in the request).
6. ConcurrentListDuringWrite: 1 writer (100 PUTs over distinct keys) + 4
   readers looping listObjectsV2 → every list parses, KeyCount <= total keys,
   no panic.

Use sync.WaitGroup + errgroup-style patterns with plain stdlib (no new deps).
Atomic counters where shared. Every goroutine's failures funnel to t.Error via
a mutex-protected collector or channels.
